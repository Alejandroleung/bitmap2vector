# vmde.exe 反编译：曲线拟合阶段的算法（实证）

工具链：Ghidra 12.2 + JDK 25（`tools/ghidra/VmReport*.java`），分析库保留在
`D:\hermes\cache\scratch\ghidra-proj`，伪 C 在 `ghidra-out/`（21 个）、`ghidra-out2/`（4 个）、
`ghidra-out3/`（18 个）。

## 结论：贝塞尔拟合 = 固定端点的最小二乘，正规方程 + 1e-5 岭项，LAPACK LU 求解

`vmde.exe` 只从 `lapack_win32.dll` 导入了**一个**例程：`dgesv_`（LU 解 A·x=B）。
它的唯一调用点是 `FUN_0049d270`（见 `ghidra-out2/0049d270_FUN_0049d270.c`）：

```c
undefined4 FUN_0049d270(int *A, int *B)   // A / B 是带维度的矩阵描述符
{
  n    = A[1];        // A 是 n×n
  nrhs = B[2];
  lda  = n;
  ipiv = alloc(int, n);
  ldb  = B[1];
  dgesv_(&n, &nrhs, *A, &lda, ipiv, *B, &ldb, &info);
  return info;
}
```

调用它的两族函数就是拟合本体：

| 函数 | 未知量 | 系统规模 | 用途 |
|---|---|---|---|
| `FUN_0049dcf0` | 2 | 2×2 | 二次贝塞尔（只解中间控制点） |
| `FUN_0049d360` | 4 | 4×4 | 三次贝塞尔（解两个中间控制点，x/y 各一） |
| `FUN_0049e380` | 2 | 2×2 | 同一拟合的另一种残差组织（权重不同） |
| `FUN_0049d8a0` | 4 | 4×4 | 三次拟合，t 由内部生成 |

三次那支的核心（`FUN_0049d360`，逐行读出来的）：

```c
t   = param_2[i];              // 每个采样点的参数值
u   = 1 - t;
b0  = u*u*u;                   // (1-t)^3
b1  = u*u*t * 3.0;             // 3(1-t)^2 t
b2  = t*t*u * 3.0;             // 3 t^2 (1-t)
b3  = t*t*t;

// 残差：端点贡献先扣掉，未知量只剩两个中间控制点
r[c] = target[i][c] - (b3*P3[c] + b0*P0[c]);          // c = x, y

// 设计矩阵 A 每行 = [b1, b2]（两个坐标交替，共 2N 行、4 列）
// 正规方程：
M = AᵀA ;  M += 1e-5 * I      // 常量 0x008de7e0 = 1e-05，只加在对角线
v = Aᵀr
dgesv(M, v)                    // LU 解 4×4
P1_new = v[0..1]; P2_new = v[2..3];

err += Σ ||B(t) - target||²    // 返回残差平方和，供分段/递归拆分决策
```

二次那支只是把基函数换成 `u²`, `2ut`, `t²`，未知量降到 2 个。

矩阵乘法用它们自己的 GEMM `FUN_005bbd40(opA, opB, opC, m, n, k, alpha, A, lda, B, ldb, beta, C)`，
前三个参数是 0x66/0x70/0x6f（'f'/'p'/'o'），是转置/布局标志，不是 BLAS 的 'N'/'T'。

## 对我们引擎的意义

1. 我们现在 `vendor/vm-tracer.js` 的拟合是贪心式（`tryLine` → `fitArc` → `fitSegStruct`，Schneider 那一套）。
   VM 用的是**每个线段一次全局最小二乘**，端点固定、只解中间控制点，再加 1e-5 岭项。
   同一组采样点下，两种做法出来的控制点不同 —— 这是"轮廓形状对、但曲线位置差一点点"的一个来源。
2. 可以直接照抄的部分：正规方程构造 + 1e-5 岭项 + LU（JS 里用带部分主元的高斯消元，与 dgesv 等价）。
3. 还缺的一环：**采样点怎么分组、t 怎么给**（在 `FUN_004a2520` / `FUN_0049f310` 一带，用残差阈值
   决定要不要二分拆分，涉及 0x006fd6b0=0.5 与 ±1/3 的差分系数）。这一层没完全读透，
   所以"分多少段"仍是我们自己的启发式。

## A/B 实测：照抄这个拟合式，反而更差（2026-11-14）

把上面这套（固定端点 + 正规方程 + 1e-5 岭项 + LU）在 `vendor/vm-tracer.js` 里实现成
`fitMode: 'ls'`（`fitCubicLS` / `fitSpanLS` / `contourToPathLS`），默认不开。实测：

| 拟合方式 | 旗帜 MAE / >32 | Logo MAE / >32 | C 段数 |
|---|---|---|---|
| 现有贪心拟合（tryLine→fitArc→fitSegStruct） | **0.0105 / 2.14%** | **0.0069 / 2.28%** | 660 / 1794 |
| LS（tol 0.15） | 0.0113 / 2.48% | 0.0078 / 2.58% | 722 / 1748 |
| LS（tol 0.08） | 0.0113 / 2.48% | 0.0079 / 2.61% | 752 / 1838 |
| LS（tol 0.30） | 0.0113 / 2.48% | 0.0078 / 2.56% | 566 / 1546 |

结论：**光换拟合式没用**。VM 的残差式最小二乘在我们自己的采样点/分段策略下更松，
贴着折线走的贪心拟合反而更接近原图。要真正复现，缺的是**分段与 t 参数化**那一层
（`FUN_004a2520` / `FUN_0049f310` 一带的残差阈值二分），不是拟合公式。
代码保留在 `fitMode:'ls'` 后面，作为后续实验入口。

## 把分段/参数化也还原了 —— 结论：拟合层不是瓶颈（2026-11-14 第二轮）

`FUN_0049c7b0`（span 预处理，逐行读出来的）确认了两件事：

1. **t = 累计弦长 / 总弦长**：逐点 `SQRT(dx²+dy²)` 累加，最后整体乘 `1/总长`
   （总长为 0 时取 1.0）。不是均匀参数化，也不是 centripetal 参数化。
2. **返回 span 内点数** `n = (j - i) - 1`，`FUN_0049e960` 用它选拟合方式：
   `n-2 ≥ 4` → 三次最小二乘；`n-2 == 3` → 二次；否则直线。
   **每段只拟合一次，没有"残差超限再切"的递归** —— 切分完全来自分割阶段。

我把这套原样实现成 `fitMode:'vmfit'`（`fitQuadLS` / `fitSpanVM` / `contourToPathVMFit`），实测：

| 拟合方式 | 旗帜 MAE / >32 | Logo MAE / >32 |
|---|---|---|
| 现有贪心（Schneider 式，残差驱动拆分） | **0.0105 / 2.14%** | **0.0069 / 2.28%** |
| VM 调度（单次 LS + 点数分档，按角点切） | 0.0157 / 3.17% | 0.0864 / 15.02% |
| 上面再加 tol 放宽到 1.8 | 0.2338 / 75.44% | 0.2285 / 35.36% |

差距的根源：VM 的 span 是**分割阶段**给出的（断点密集），我们只有角点检测，
长 span 用一根三次曲线必然贴合不住波浪形轮廓。

**结论（重要）**：曲线拟合公式、t 参数化、正规方程细节都已还原且照抄了，
但抄过来更差 —— 我们和官方的差距主要不在拟合，而在
（a）**分割粒度**（region 级 vs 我们的 contour 级）、（b）**亚像素边界定位**。
拟合层到此为止，`fitMode` 保留 `'ls'` / `'vmfit'` 两个实验开关，默认仍是贪心。

## §3 运行期实测（frida 内部 hook）—— 2026-11-14

绕开 cua 驱动读不到屏幕外窗口的问题，改用 Win32 `PrintWindow` + `PostMessage`
（`D:\hermes\cache\scratch\frida\vm_click.py`），在 vmde.exe 内部四个地址打点：

| 地址 | 含义 | 抓到的量 |
|---|---|---|
| 0x49e960 | span 调度 | 每段起点/终点索引 |
| 0x49d360 | 三次最小二乘 | 点数 n、t 数组 |
| 0x49dcf0 | 二次最小二乘 | 点数 n、t 数组 |
| 0x49d270 | dgesv 包装 | 系统维度 |

一次「全自动」矢量化的实测（旗帜图 507×258）：

```
span=60（仅前 60 条被记录）  cubic=40  quad=102  solve=40
span 跨度分布：{1: 40, 2: 20}      ← 每段只跨 1–2 个断点，即 3–4 个采样点
cubic n=4  t=[0.1999, 0.3999, 0.5999, 0.8000]   ← 近似均匀，但带 ±0.001 抖动
quad  n=3  t=[0.2512, 0.5018, 0.7514]
```

**完整统计**（一次全自动矢量化的全部 246 条事件）：

| 项 | 数值 |
|---|---|
| cubic 调用 | 40 次，n 全为 4 |
| quad 调用 | 102 次，n 全为 3 |
| solve（dgesv 包装） | 40 次（只对应三次那一支；二次的 2×2 走另一条路） |
| span 跨度 | 1 个断点 40 次、2 个断点 20 次 |
| t 是否均匀 | **142/142 全部严格均匀**（±0.002 内） |

结论（修正前一版）：
1. **t 是严格均匀参数化**，不是弦长归一化 —— n=4 时 t=0.2/0.4/0.6/0.8，
   n=3 时 t=0.25/0.5/0.75。所以 n 表示的是**内部点个数**：
   三次段 = 2 端点 + 4 内部点（12 个方程解 4 个未知量），
   二次段 = 2 端点 + 3 内部点（10 个方程解 2 个未知量）。两档都是超定最小二乘。
   `FUN_0049c7b0` 里那段累计弦长计算存在，但没有参与最终的 t（点列本身已等距）。
2. **span 极短**：官方是"密集断点 + 短段拟合"，不是"少量长曲线"；
3. 二次段远多于三次段（102 : 40），且二次段不经过 `FUN_0049d270`。

补充实测：把 `tmode:'uniform'` 与弦长两版都跑一遍四个官方样本，**结果一模一样**
（0.0091/0.0116/0.0105/0.0052 vs 0.0091/0.0117/0.0105/0.0052）——
因为 `vmSpan=16` 时采样点本身就近似等距，两种参数化退化成同一个东西。

  这张是"多色调抗锯齿 logo"，差距落在**分割粒度**上，不是拟合。
